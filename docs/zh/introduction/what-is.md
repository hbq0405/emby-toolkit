# 项目概览

ETKvNext 是 ETK 的新版实现。它沿用成熟的媒体识别、整理、订阅和洗版思路，但把数据、配置、任务和媒体服务重新组织为一套独立系统。

## 面向用户的工作方式

可以把 ETKN 理解成四个相互连接的工作区：

1. **资源中心**负责找到资源：共享池、Telegram 频道、MoviePilot、re0 和手动链接都在这里接入。
2. **媒体处理**负责把资源变成可用媒体：识别身份、整理目录、生成 STRM、准备元数据和媒体信息。
3. **订阅中心**负责持续追踪：追剧、演员、合集、榜单和影视探索产生的需求都会进入统一处理。
4. **任务中心**负责记录过程：每次处理都有根任务、阶段、日志、重试和结果，不需要只看最后几行容器日志猜原因。

## 内置媒体服务

ETKN 内置了兼容 Emby/Jellyfin 客户端习惯的媒体服务接口。客户端可以使用 ETKN 提供的媒体服务地址浏览媒体库、查看详情和播放，不需要再为新版主流程单独部署一套外部 Emby。

- 管理控制台和管理 API 默认使用 `5257`。
- 媒体服务和虚拟媒体库默认使用 `8097`。
- 本地资源由 ETKN 直接提供；115、分享和共享池等非本地资源必须解析为直链后以 `302` 交给客户端，不通过 ETKN 长时间中转媒体流。

## 数据和部署

- PostgreSQL 保存配置、用户、媒体、订阅、任务和整理记录。
- 容器启动时执行版本化数据库迁移，已执行的迁移不会被静默修改。
- `/config` 保存配置文件、图片仓库、Telegram 会话和其他需要跨容器重建保留的运行数据。
- Docker Compose 是推荐的安装方式，也适合直接改造成 Unraid Compose。

## 不是哪些东西

- 它不是旧版 ETK 的换皮前端，旧版数据库不会自动被新版直接读取。
- 它不是只负责生成 STRM 的小工具，整理完成后还会继续执行元数据、媒体信息、图片和媒体库更新。
- 它不是把所有外部服务都设为必选的单体流程；每个来源和增强能力都可以单独授权、停用或排查。
